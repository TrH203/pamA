pamA Cloud: máy giữ bản gốc, server lo phần chia sẻ

Tài liệu này mô tả cách pamA chạy khi người dùng chỉ cài lệnh pama và kết nối tới một server từ xa: thành phần nào nằm ở đâu, dữ liệu nào được đi qua mạng, cách deploy server lần đầu, pipeline CI/CD và kế hoạch landing page.

1Tổng quan

pamA cho phép một người code cùng AI agent (Claude Code, Codex) để agent trả lời câu hỏi của người khác về công việc đó. Chỉ ý chính và quyết định được chia sẻ; bí mật được lọc bỏ. Cùng một codebase chạy ở ba chế độ:

Chế độNgười dùng cài gìServer ở đâuAi vận hành
LocalDesktop app hoặc pama + server sidecar (PGlite)Trên máy, 127.0.0.1Người dùng
Self-hostpamaDocker Compose của một nhómNhóm tự host
Cloud (tài liệu này)Chỉ pamaServer pamA Cloud, nhiều workspaceChúng ta

Ở chế độ remote (spec 004), máy chạy hook ghi phiên, che bí mật (Lớp 1), soạn digest bằng Rust và giữ bản gốc của mọi digest. Server giữ phần cần truy cập từ bên ngoài: duyệt digest trên web, Ask Link, hộp thư câu hỏi chuyển tiếp, audit và console.

Nguyên tắc không đổi: transcript gốc và transcript đã che đều không bao giờ được gửi lên server pamA. Thứ duy nhất rời máy là digest (bản tóm tắt bằng tiếng Anh đã che bí mật), và chỉ với project đã bật sync.

2Kiến trúc local – cloud

Màu xanh rêu là phần chạy trên máy, xanh dương là server, vàng nâu là dịch vụ bên ngoài. Đường nét đứt màu cam là ranh giới tin cậy: chỉ ba luồng đánh số được phép đi qua.

1POST /v1/sync/drafts: digest đã che, đi từ outbox lên server. Thử lại khi mất mạng.
2GET /v1/sync/changes: quyết định duyệt trên web được kéo về máy (tối đa 1 lần/60 giây). Lệnh xoá trên máy luôn thắng.
3Lệnh pama gọi API của owner bằng device token lưu trong keychain.

3Dữ liệu nào nằm ở đâu

Chỉ ở trên máy

  • Transcript gốc của agent (đọc tại chỗ)
  • Sự kiện đã qua Lớp 1 (chỉ gửi tới model soạn do bạn chọn)
  • Bản gốc mọi digest và trạng thái của nó (remote_digest)
  • Device token, API key model soạn (OS keychain)
  • Danh sách project bật sync (remote.sync_projects)

Trên server

  • Digest của project đã bật sync (bản nháp hoặc đã duyệt)
  • Item đã embed để truy xuất cho Ask Link
  • Ask Link, câu hỏi, hộp thư chuyển tiếp, audit (giữ 180 ngày)
  • Tài khoản email, workspace, thiết bị (token đã băm scrypt)
  • API key BYO của workspace, mã hoá bằng PAMA_SECRET

Gửi tới bên thứ ba

  • Model soạn: văn bản phiên đã che (nếu chọn API thay vì Ollama)
  • Model trả lời: câu hỏi + item trong phạm vi link
  • Embedding: nội dung item
  • SMTP: địa chỉ email, link đăng nhập

Ba lớp che bí mật

LớpChạy ở đâuLàm gì
Lớp 1Máy (Rust)222 luật gitleaks + luật pamA, bỏ cả kết quả tool đọc file .env/key. Chạy trước mọi model. Chạy lại trên mọi chuỗi model soạn trả về.
Lớp 2Server, lúc nhận draftChạy lại các luật và phân loại item (business_sensitive, infra, customer).
Lớp 3Server, trước khi hiện câu trả lờiQuét lại câu trả lời, kiểm tra chủ đề bị cấm, model giám khảo tìm rò rỉ. Lỗi bất kỳ thì từ chối và đề nghị chuyển câu hỏi cho bạn.

4Luồng đăng nhập thiết bị

Kiểu RFC 8628: máy xin một mã, bạn duyệt mã đó trên web sau khi đăng nhập bằng email, máy nhận token đúng một lần.

sequenceDiagram
  autonumber
  participant CLI as pama (máy)
  participant S as Server pamA
  participant B as Trình duyệt của bạn
  participant M as Hộp thư
  CLI->>S: POST /v1/auth/device/start (tên máy)
  S-->>CLI: device_code, user_code ABCD-EFGH, hạn 10 phút
  CLI->>B: mở /?device=ABCD-EFGH
  B->>S: POST /v1/auth/login (email, next)
  S->>M: link đăng nhập
  M->>B: bấm link, quay lại trang duyệt
  B->>S: POST /v1/auth/device/approve
  loop mỗi 2 giây
    CLI->>S: POST /v1/auth/device/token
    S-->>CLI: 428 authorization_pending
  end
  S-->>CLI: 200 device token (chỉ giao một lần)
  CLI->>CLI: lưu token vào keychain, mode = remote

Lệnh: pama login --server https://app.<tên-miền>. Qua SSH dùng --no-browser và mở link in ra ở máy khác. pama logout thu hồi token trên server.

5Luồng digest: từ phiên làm việc tới server và quay về

sequenceDiagram
  autonumber
  participant A as Agent (Claude Code, Codex)
  participant H as pama hook
  participant D as Drafter + kho SQLite
  participant L as Model soạn
  participant S as Server pamA
  participant O as Bạn (web)
  A->>H: kết thúc phiên
  H->>D: xếp hàng, trả về trong 1,5 giây
  D->>D: Lớp 1 che bí mật trên sự kiện
  D->>L: transcript đã che (tối đa 48.000 ký tự)
  L-->>D: JSON digest
  D->>D: che lại mọi chuỗi, áp giới hạn, lưu bản gốc
  D->>S: POST /v1/sync/drafts (chỉ project đã bật sync)
  S->>S: Lớp 2, lưu nháp hoặc tự duyệt
  O->>S: duyệt, sửa hoặc bỏ trên console
  D->>S: GET /v1/sync/changes?since=cursor
  S-->>D: trạng thái mới, digest đã sửa
  D->>D: cập nhật bản gốc trên máy
  • Không có daemon: pama capture drain chạy tách ra sau hook, gửi outbox và kéo thay đổi về.
  • Mất mạng: draft nằm trong outbox, gửi lại với backoff tối đa 60 giây.
  • Tắt sync một project (pama sync disable) gửi tombstone; server xoá draft và digest của project đó. Draft cũ đến sau tombstone bị từ chối (409).

6Luồng Ask Link

  AM-->>S: câu trả lời có trích dẫn
  S->>S: Lớp 3 kiểm tra
  alt qua kiểm tra
    S-->>V: câu trả lời + trích dẫn
  else bị từ chối
    S-->>V: đề nghị chuyển câu hỏi
    S->>O: vào inbox (pama inbox hoặc console)
  end

Mọi câu hỏi đều ghi vào audit. Năm lần nhập sai PIN/OTP khoá người hỏi và IP trong 15 phút.

8Các bước deploy lần đầu

  1. Merge nhánh 004-thin-client vào main và gắn tag (ví dụ v0.4.0). Workflow release.yml sẽ build image ghcr.io/trh203/pama/server và binary pama.

  2. Mua tên miền, tạo Lightsail 2 GB (Ubuntu 24.04), gắn IP tĩnh, mở cổng 22 (chỉ IP của bạn), 80 và 443. Đặt AWS Budgets cảnh báo ở $15/tháng.

  3. Chạy deploy/cloud/bootstrap.sh trên VM: cài Docker và AWS CLI, thêm swap, clone repo vào /opt/pama, đặt lịch backup.

  4. Trỏ DNS app.<tên-miền> về IP của VM.

  5. Xác minh domain gửi mail trên SES/Resend (SPF, DKIM) và lấy thông tin SMTP.

  6. Điền deploy/cloud/.env theo mục 7, sinh bí mật bằng openssl rand -base64 36, cất bản sao vào password manager.

  7. Khởi động và kiểm tra:

    docker compose -f deploy/cloud/docker-compose.yml up -d
curl -s https://app.<tên-miền>/v1/health
# "mode":"cloud", capabilities có device_login, drafts, changes

  8. Thử end-to-end từ một máy sạch: pama login --server …, pama init --sync, kết thúc một phiên, duyệt trên web, tạo Ask Link, hỏi thử, rồi pama doctor.

  9. Bật sao lưu hằng đêm và thử khôi phục một lần vào DB trống.

Pipeline đề xuất

flowchart LR
  PR[Pull request] --> CI[ci + docker + evals]
  CI -->|merge| MAIN[main]
  MAIN -->|tag v*| REL["release.yml: image ghcr.io + binary pama"]
  REL --> GATE{Duyệt môi trường production}
  GATE --> BK[pg_dump trước khi deploy]
  BK --> PULL["SSH: compose pull + up -d với tag mới"]
  PULL --> HC{"health ok trong 2 phút?"}
  HC -->|có| SMOKE["smoke: health, login start, Ask Link"]
  HC -->|không| RB[quay về tag cũ]
  SMOKE --> DONE[Xong]
  MAIN -->|đổi landing| LP["landing.yml: build + Pages"]
  • Môi trường production trong GitHub với người duyệt bắt buộc; secret SSH key và host chỉ nằm ở đó.
  • Ghim phiên bản: VM chạy PAMA_IMAGE=ghcr.io/trh203/pama/server:vX.Y.Z, không dùng latest, để rollback chỉ là đổi lại tag.
  • Migration chạy lúc khởi động, nên backup trước khi deploy là bước bắt buộc; migration nên luôn thêm cột/bảng thay vì xoá để rollback image vẫn chạy được.
  • Binary pama: release đã upload lên GitHub Releases; cần thêm install.sh và ký/notarize macOS (đang có scripts/sign.sh chưa commit).

10Landing page

Mục tiêu: một người mới đọc trong 30 giây hiểu pamA làm gì, tin rằng transcript không rời máy, và cài được pama bằng một lệnh.

Mở đầuMột câu nói rõ lợi ích, lệnh cài đặt, nút “Dùng pamA Cloud” và “Tự host”

Checklist trước khi bấm deploy

  • Nhánh 004 đã merge, CI xanh, có tag release và image trên ghcr.io
  • Tên miền, DNS cho app., SMTP đã xác minh
  • deploy/.env đủ biến, bí mật đã cất ở nơi khác
  • deploy/cloud/ đã thử trên VM thật (compose đã viết, mới kiểm tra cú pháp)
  • Quyết định chính sách đăng ký
  • Backup hằng đêm chạy và đã thử khôi phục
  • Thử end-to-end từ một máy chỉ cài pama
  • deploy.yml có bước backup, health check, rollback
